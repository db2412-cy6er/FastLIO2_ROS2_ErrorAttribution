### 2.2 SLAM 算法角度三个最核心突出点（展开版）

**突出点 ①：在滤波器"内部"构建可观测性量化器——基于真实参与 IEKF 更新的测量 Jacobian 构造几何 Hessian，实现零侵入的退化检测（P1）**

不是从点云外观"猜"退化，而是直接在 FAST-LIO2 每次 LiDAR update 收敛后，取**真实参与状态更新的逐点 point-to-plane 测量 Jacobian 行** `j = h_x[i, 0:6]`，累加成 6×6 **LiDAR geometric Hessian**：
`Ht = Σ n·nᵀ`（平动块，世界系法向量），`Hr = Σ (p×n)(p×n)ᵀ`（转动块），`H6 = Σ j·jᵀ`。随后做特征分解：`trans_ratio = λmin(Ht)/λmax(Ht)`、`rot_ratio = λmin(Hr)/λmax(Hr)`、`weak_direction = H6 最小特征值对应特征向量`。其中平动/转动分量的坐标系约定（列 0-2 世界系、列 3-5 body 系）在 `.msg` 注释里显式固化，避免后续 P2/P3/P4 用错坐标。为保证"零侵入"，检测器开启标志默认 `false`，且通过 baseline/degen 同 bag 各 3 次回放验证轨迹数值等价（Welch t 检验 p=0.177），从代码路径与统计两个层面证明"只读不改"。

同时设计了**双检测器架构**：内嵌 exact（几何 Hessian，看算法内部真实约束）+ 外部 proxy（`degeneracy_proxy.cpp` 订阅 `/cloud_registered`，用 kNN/PCA 重估局部平面结构）。关键实证结论：**open_ground 上两者 100% overlap；corridor 只有 proxy 先检出、single_plane 只有 exact 检出**——单检测器必漏检一类退化，验证了双视角互补的必要性。还顺带定位到"exact 检测阈值太严"（`threshold_t=0.02` 时走廊退化帧检出率 0%，放宽到 0.10~0.15 后 99.6%），证明"不报警 ≠ 没退化，可能是灵敏度问题"。

**突出点 ②：从"检测"到"归因"——三层误差归因框架（Health→Attribution→Consequence），并证明"退化 ≠ 必然大误差"（P2）**

P2 不是简单堆阈值，而是把 LIO 故障按风险源拆成**可同时成立的多标签 flags**：`is_geometry_degen / is_matching_failure / is_imu_low_excitation`，各自输出 0~1 heuristic severity（margin）。为此在 FAST-LIO 内嵌发布 `/lio/health`（聚合 geometry/matching/covariance/IMU 激励四路原始信号），外挂 rule-based `attribution_node` 输出 `/lio/error_attribution`。验证方法学是亮点：**① fault injection 剧本**（dropout 丢点 / fov_crop 视场收缩 / outlier 离群点 / noise 高斯噪声，固定 seed，已知时段）；**② 两层验证**（分类 precision/recall vs 场景标注；后果严重度 vs GT 误差）；**③ 数据划分纪律**（只用 corridor_run1 标定，新走廊/室内/单面墙/held-out fault 做验证，杜绝数据泄漏）。冻结后指标：干净走廊 recall 1.00、正常室内无 flag 误报（recall 0.93）、单面墙 recall 1.00、fault 注入 precision 全部 1.00 / recall 0.65~0.77。更重要是一个"非结论"：**走廊退化 ATE 仅 ~0.034 m，single_plane 退化却达 7.4 m，人为强故障 4.08 m**——"检测到退化"与"误差变大"解耦，检测报告的是几何可观测性风险，误差后果必须由 GT 量化。这一框架解释了为什么很多退化检测论文里"检出了却不见误差涨"。

**突出点 ③：用严格实验方法学系统证伪三条直觉"自适应"路线，把研究收敛到正确方向（P3/P4/P5 组合拳）**

这是最体现科研品味的一点。接 P2 的 flags+severity，我依次实现了三条"听到报警就动手"的方案并逐一做了严格的 median-of-3 A/B：**P3 整体降权**（把编译期常量 `LASER_POINT_COV` 换成运行时 `lidar_meas_cov_`，双通道 severity 映射到 R 放大倍数，fast-attack/slow-release EMA，3s 降权上限）→ 结果：normal 零影响、corridor 无显著差异、single_plane 变差 4.5×、holdout/stress fault 变差 14×/8.7×；**P4 方向性抑制**（在 ESKF state correction 层把 dx 沿 weak direction 投影 `Π_β(v)=v−(1−β)(v·w_t)w_t`，并同步投影 K 行保持协方差一致，只允许 geometry-bad ∧ matching-ok 触发）→ 结果：normal/corridor 安全、single_plane holdout 变差 3.7×、fault 场景 15~50% 改善倾向（但样本方差大、机制未明）；**P5 当前帧测量拒绝**（在 IEKF 第一次迭代后按相对基线骤降 + 残差异常拒绝整帧，恢复 x/P 为 propagation 态并跳过地图插入）→ 结果：clean/geometry 零误杀零侵入，但持续 fault 场景 5.8~26× 变差，并定位到"拒绝→漂移→拒绝"负反馈。三条路线收敛到同一个强结论：**FAST-LIO 原版滤波器的容错已经很强，任何"把状态估计从 LiDAR 弱约束交给 IMU"的介入在 IMU 精度有限时都是净损失；唯一被验证有效的是"检测 + 归因 + 门控"（P2/P4 matching gate）**。这套"数值 sanity test → synthetic test → C++/Python parity check → 标定/验证分离 → median-of-3 A/B → 诚实负面结论"的完整流程，本身就是 SLAM 岗位最看重的**可复现实验能力**证据。

### 2.3 ROS / C++ 开发角度三个最核心突出点（展开版）

**突出点 ①：深度阅读并最小侵入改造第三方 LIO 源码——直接修改 FAST-LIO2 的 ESKF/IEKF 求解器内核**

改造点都在滤波器核心：
- `esekfom.hpp` 的 `update_iterated_dyn_share_modified()`：① 将写死的测量协方差改为运行时变量 `lidar_meas_cov_`（P3 自适应权重）；② 增加 state-layer 方向性投影（插入点 A：`dx_` 计算后、`boxplus` 前投影 dx 平动分量；插入点 B：`P_ = L_ − K_x P_` 前投影 K_x 的 pos 三行，保证协方差不自相矛盾）；③ 增加 first-iteration reject hook（第一次 `h_dyn_share()` 之后、K 计算之前回调，拒绝时显式 `x_=x_propagated; P_=P_propagated`）。
- `laserMapping.cpp`：新增 `compute_geometric_hessian()`（读 `h_x` 累加 H6/Ht/Hr）、`publish_degeneracy_score()`、P2 health 聚合、P3 adaptive controller、P4 `update_directional_cache()/compute_directional_trigger()/compute_directional_matching_gate()`（Ht 时间累积解决特征向量符号歧义）、P5 robust gate 状态机。
- **工程纪律**：所有改动默认 `false`（零侵入），每个新机制都有 C++/Python parity check（P3 max|err|=5e-6；P4 535/535 帧一致率 100%）证明"改对了"，再谈效果。这体现对状态估计源码（esekfom/IKFoM、Eigen、ikd-Tree）的掌握和克制、干净的工程习惯。

**突出点 ②：自建"消息接口包 + 评测编排包"双包体系，把实验做成一等公民**

- `src/lio_interfaces/`（ament_cmake + rosidl 接口包）：4 个自定义 msg（`DegeneracyScore / DegeneracyIteration / LioHealth / ErrorAttribution`），字段注释里写清理论口径与坐标系约定（例如 "geometric Hessian 仅反映 scan-to-map 几何约束，不含噪声/协方差"），从消息层防语义漂移。
- `src/lio_evaluation/`（C++/Python 混合包）：`degeneracy_proxy.cpp` C++ 节点；30+ 个 Python 脚本完成采集/录制/监控/评测/编排（`recorder_node` 落 TUM + 多路 CSV、`monitor_node` 用 psutil 记录 CPU/内存、`compute_metrics` 时间对齐 + 调 evo 算 ATE/RPE、`run_experiment` 支持 prepare/run-online/replay/eval/all 五段式、`generate_worlds` 生成受控退化场景、`lidar_fault_injector`、`drive_node` 避障漫游、`health_watch` 看门狗等）。

### 4.1 ESKF / IEKF / FAST-LIO 原理类

**Q1：FAST-LIO2 的整体框架？为什么用 ESKF 而不是直接对完整状态做 EKF？**

A：FAST-LIO2 是 LiDAR-IMU 紧耦合里程计：IMU 以 100Hz+ 做**状态传播**（propagation），LiDAR 帧（10Hz）到达时把帧内 IMU 积分结果作为先验做**迭代测量更新**（IEKF correction），两者都在**误差状态（error-state）**上做，所以叫 ESKF（error-state Kalman filter）。用误差状态的原因：① 姿态用 SO(3)/四元数流形表示，误差态 δθ 是切空间小量，可近似为欧氏空间做标准卡尔曼递推，避免对四元数直接加高斯噪声带来的归一化/奇异性问题；② 误差态量级小，一阶线性化精度足够，且可把 IMU bias 等小量状态解耦；③ FAST-LIO 的迭代更新（IEKF）复用误差态再做一次 Gauss-Newton 式迭代优化，逐次用更准的位姿重新做 scan-to-map 匹配并刷新残差与 Jacobian，等效于在流形上做最大后验估计。地图侧，FAST-LIO2 用 **ikd-Tree**（增量式 KD-Tree）维护全局地图，支持增量插入、下采样与动态删点，省去传统体素地图（如 FAST-LIO 的局部地图）的维护开销，并直接在整张增量地图上做 point-to-plane 最近邻匹配。

**Q2：point-to-plane 残差与测量 Jacobian 怎么写？为什么 Ht/Hr 能反映"可观测性"？**

A：对地图上的平面点 q 及其单位法向量 n，当前 LiDAR 点 p（经外参转到 body）在当前估计位姿 (R,t) 下的残差为 `z = nᵀ(Rp + t − q)`。对误差状态 δx=[δp,δθ,…] 求导，得到测量行 Jacobian `h = [nᵀ, nᵀ(Rp)×…]`（平动项是世界系法向量；转动项约化为 p×n 形式，落在 body 系）。把一帧内所有有效点行向量累加外积 `H = Σ hᵀh`（我代码里拆成 Ht=Σnnᵀ、Hr=Σ(p×n)(p×n)ᵀ、H6 全 6DoF），这就是 **measurement/geometric Hessian**：它量化"这一帧点云对 6 个自由度各能施加多少约束"。对 Ht/H6 做特征分解，最小特征值方向就是**几何上最不可观测的方向**：比如长走廊，两侧平行墙只约束横向 y 与部分转动，纵向 x 几乎没有法向量分量，于是 Ht 在 x 方向特征值极小 → `trans_ratio=λmin/λmax` 趋近 0。特征向量 `weak_direction` 就是后续做方向性抑制/误差方向分析要用的那个方向。注意口径：它只含 scan-to-map 几何约束，不含噪声与先验协方差，因此叫 geometric Hessian 而不是完整信息矩阵——这个口径我在 msg 注释里写死了，防止和论文里的 CRLB/Fisher 信息矩阵混淆。

**Q3：什么是"退化（degeneracy）"？它在物理上意味着什么？**

A：退化指某场景的几何结构不足以唯一约束机器人的全部（或部分）自由度。数学上表现为 measurement Hessian 奇异或病态：沿某个方向（如走廊纵向、单面墙的墙内方向、空旷地面除高度外的水平方向）激光无论怎么匹配都"看不出位移"，信息增益趋近零。物理上，滤波器在这类方向上只能依赖 IMU 积分与运动先验，误差随时间累积（若该方向连 IMU 也无法观测，例如单面墙法向外的平移——其实墙的法向约束很强，真正弱的是墙平面内两个方向）。我实测的三类场景：corridor（trans_ratio≈0.047，纵向约束弱）、single_plane（平面内两方向几乎无约束，trans_ratio≈0.0004，ATE 1.75~7.4m 视滤波器状态）、open_ground（仅地面，几乎完全退化，ATE≈1.8m）。**重要结论（P1.3/P2 实证）**：退化≠必然大误差——corridor 全程退化但 ATE 仅 ~5cm，因为 IMU+其余强约束把漂移压住了；误差大小取决于"不可观测方向是否被 IMU 以外的东西兜住"。

**Q4：IEKF 与普通 EKF 的区别？你说的 first-iteration 与 final-iteration 指什么？**

A：EKF 在预测点做一次线性化就完成更新；IEKF（迭代扩展卡尔曼滤波）把更新变成一个迭代优化：每次迭代用当前估计位姿重新做 scan-to-map 最近邻匹配，重新计算残差与 Jacobian，再做一次卡尔曼/高斯牛顿修正，直到收敛（FAST-LIO 里默认迭代几次并在残差变化小于阈值时提前停）。这样能显著缓解"大误差下一次性线性化不准"的问题。在本项目里，"first-iteration"指**第一次迭代**，此时匹配用的位姿是 IMU propagation 后的状态（还未被本帧 LiDAR correction 污染）；"final-iteration"指收敛后那一轮。这个区别非常关键：P2 的匹配质量阈值是在 final-iteration 上标定的，而 P5 要做"当前帧尽早判断是否拒绝测量"，只能用 first-iteration 信号——我通过 P5.0 离线预演发现 first/final 的分布差异很大（干净场景两者接近，但 fault 场景 first-iteration 的残差远好于 final，因为坏 correspondence 是在迭代过程中才把残差推高的），**P2 的 absolute 阈值直接搬到 first-iteration 必然误判**（normal_indoor 干净帧会误拒 99.8%），必须改用相对滚动基线。

### 4.2 退化检测与"零侵入"类（P1）

**Q5：内嵌精确检测器（exact）和外部几何代理检测器（proxy）各自怎么工作？为什么需要两个？**

A：exact 检测器写在 FAST-LIO 内，IEKF update 收敛后读取**真实参与更新的 h_x**，累加 H6/Ht/Hr 并发布分数——它反映"算法内部此刻到底获得了多少几何约束"，最准确但只能看到滤波器的视角；proxy 检测器是独立 C++ 节点，订阅 `/cloud_registered` 点云，用 kNN+PCA 估计局部法向、统计平面占比等外部几何量，重新估计退化程度——它不依赖滤波器内部实现，是"独立第三方视角"。需要两个是因为真实实验发现**灵敏度互补**：open_ground 上两者 100% 一致；corridor 中 proxy 先检出而 exact 因 `threshold_t` 太严漏检；single_plane 中 exact 检出而 proxy 因平面占比统计口径漏检。**单用任何一个都会漏检一类退化**，双视角交叉验证也提高了检测结论可信度。代价是两者不会逐帧完全一致（overlap 不一定高），所以验收不看强相关，而看"事件级 overlap 与互补覆盖"。

**Q6："零侵入"是怎么做到并证明的？为什么这件事重要？**

A：做法上，所有检测与后续机制都满足：① 默认参数 `enable=false`（P3/P4/P5 都默认关）；② 检测器只在 IEKF 更新收敛后**读** h_x、**从不回写**状态；③ 新机制改动集中在函数参数/回调点，不改滤波器原有数值路径。证明分两层：代码路径复核（`is_degenerate` 只发布不写状态）+ **统计验证**——同一 corridor bag 用 baseline（检测关）与 degen（检测开）各回放 3 次，两组 ATE 差异（~0.009m）小于 baseline 自身组内极差（0.015m），Welch t 检验 p=0.177 不显著，因此"degen 比 baseline 准 1.6cm"的初看结论被判定为回放噪声。这件事重要的原因是：任何"改进算法"实验必须先排除"我根本没改坏/根本没生效"或"差异只是噪声"，零侵入设计让我能把检测、归因、控制逐层打开做干净消融，不会把多机制效应混在一起。

**Q7：corridor 的弱方向实测是 z（竖直）而不是走廊纵向 x，你如何解释？这说明什么？**

A：这是 P1.3 的一个"反直觉但数据确凿"的发现。机理是传感器+环境的组合几何：Livox MID-360 视场是 −7°~+52°，**约 89% 的光束朝上**，在 0.8m 宽窄走廊里两侧墙占满视场（法向≈±y），所以 y（横向）约束最强、从不退化；地面只在 −7° 底部条带可见，仅约 6% 的点，所以 z（高度）约束反而最弱（81.9% 帧弱方向指向 z）；x（纵向）约束来自走廊尽头与沿途物体，只有 18% 帧成为弱方向。这说明退化检测的结果高度依赖**传感器视场 × 环境结构**的组合，不能凭"走廊=纵向退化"的直觉下结论。第二个发现：即使弱方向是 z、exact 报 99.6% 帧退化，ATE 也只有 ~5cm 且误差只有 58% 沿弱方向、与 trans_ratio 相关性极低（Pearson −0.15）——再次印证"几何可观测性弱"与"误差增长"是两个概念，后者还取决于滤波器鲁棒性与其余自由度的约束。这个案例面试时很加分，因为它展示你会用数据修正直觉。

### 4.3 评测方法学类（GT/metrics/可复现性）

**Q8：你是怎么拿到真值、怎么算 ATE/RPE 的？为什么轨迹要先对齐再算误差？**

A：Gazebo 的 URDF 里给机器人装了 P3D 真值插件，直接发布 world 系下机器人真实位姿 `/gt_odom`（100Hz），`ground_truth_bridge` 节点把它聚合成 `/gt_path` 并可导出 TUM 格式。离线评测（`compute_metrics.py`）做四件事：① 时间对齐（把 GT 插值到 FAST-LIO 里程计时间戳）；② **Umeyama / SE(3) 刚体对齐**（把估计轨迹与 GT 对齐，消去两套系统之间的初始位姿差），用 `correct_scale=False`（不缩放，因为里程计不该有尺度误差；若缩放了反而会掩盖真实漂移）；③ 调 evo 计算 ATE rmse/mean/max 与 RPE；④ 合并运行耗时/内存到 `result.yaml`。**为什么必须对齐**：LIO 是增量里程计，它在自己的 odom 系下输出，与 world 系 GT 之间差一个固定的初始位姿（甚至 yaw 差 90°，因为出生位姿有朝向）；不对齐就比误差会把"初始位姿差"误算成"定位误差"——我曾踩过这个坑（rot_err 虚高到 90°，对齐后仅 0.71°，见 P1.1 §8），后来统一用对齐后姿态算旋转误差。

**Q9：为什么 A/B 对比必须"同一输入跑 3 次取中位数"？**

A：因为真实回放实验发现 **FAST-LIO 运行本身存在非确定性**：同一个 bag、同一份参数连续回放 3 次，ATE 会在 0.104~0.204m 之间浮动，帧数（847~851）都不完全一致。来源是回放时序抖动（rosbag 时钟/线程调度/KD-tree 并行等）。一开始我们甚至误以为两次回放"完全一致"，第三次运行就露馅了，结论已撤回并写进报告。因此我规定：**所有 P3/P4/P5 正式 A/B 一律同一输入各跑 ≥3 次取 median，且只承认"组间差大于组内运行噪声 spread"的差异**。这套纪律让"0.01m 的改进"不会再被误读为算法提升。

**Q10：受控退化场景怎么生成？故障注入怎么保证"剧本"可信？**

A：受控退化场景（corridor/single_plane/open_ground）不是手工搭的静态 world，而是 `generate_worlds.py` 在实验期按模板生成到实验目录，生成后自动自检（世界加载/落地/雷达话题健康门禁），保证"这次实验的几何确实是我们要测的退化几何"。故障注入（`lidar_fault_injector.py`）支持四类原语：**dropout**（随机丢 ratio 比例点，模拟雾/遮挡）、**fov_crop**（只留某方位/俯仰范围，模拟视场收缩）、**outlier**（把 ratio 比例点替换成随机离群点）、**noise**（叠加 σ 高斯测距噪声），按 yaml 剧本在指定秒段生效且固定随机 seed。之所以"剧本可信"，是因为故障类型/时刻/seed 全部已知可复现，于是"标准答案"（哪段时间该判成什么故障）是确定的，可以直接算 precision/recall。还发现并修过一个时间基准 bug：injector 的 t0 与 health 时间戳起点不一致，导致故障效应被错位 1~3s、召回率被低估一半——修法是统一减首帧时间 + 故障段取 ±3s 缓冲。

**Q11：为什么用 precision/recall 而不是单一准确率来验收归因？为什么 precision 全 1.00 值得说？**

A：三类风险源（几何退化/匹配失败/IMU 激励不足）里，正常帧远多于异常帧（类别不平衡），准确率会被"全猜正常"刷高，没有意义；所以要分开看"报的准不准"（precision=报出来的是否真有问题）与"漏没漏"（recall=真有问题的是否报出来了）。对本项目而言，**precision=1.00 意味着全部 hold-out 实验里归因模块一次都没有误报**——这对"把归因结果当作后续自适应控制信号"是硬前提：宁可漏报（保守不动作），不能误报（乱动作把好状态搞坏）。recall 则因场景而异（几何类 1.00、fault 类 0.65~0.77），漏检主因是 fault 实际效应与剧本时间 1~3s 错位，属于注入链路误差而非检测器失效（质量型故障 dropout 之后加 outlier/noise 段的 recall 是 1.00）。

### 4.4 误差归因设计类（P2）

**Q12：归因模块的三个 flag 为什么要"可同时成立"？severity 和 dominant label 各是什么角色？**

A：真实 LIO 故障是复合的：机器人在退化走廊里停着不动，"几何退化"和"IMU 激励不足"同时为真；硬做成互斥单分类（如"到底是几何还是 IMU"）是错误建模。所以核心输出是**多标签 flags + 每类 0~1 severity**：`is_geometry_degen`（由 P1 的 trans_ratio/score 判定）、`is_matching_failure`（由 effective_feature_ratio 相对滚动基线骤降 + 残差 p90 判定，只有"特征少且残差差"才算，规避"dropout 保留的 20% 点匹配仍有效"的误杀）、`is_imu_low_excitation`（纯 IMU 信号判定，不含几何，避免同义反复）。severity 是**距规则阈值的归一化启发式裕度**，不是概率置信度，所以命名 margin 而非 confidence；`dominant_risk_label` 只是 `argmax(severity)` 的显示摘要，供人看、给图着色。还有两个语义修正：IMU 低激励只描述"运动激励不足影响 bias 可辨识性"，**不等于 IMU 测量失效**，因此 P3 降权控制通道特意不收 IMU 信号，只当观测哨；"匹配失败"与"几何退化"在 P2 命名上分得清清楚楚，避免把两类完全不同的问题混成一个"退化"。

**Q13：matching failure 用什么特征判？为什么用"相对滚动基线"而不用绝对阈值？**

A：特征上同时看"量"与"质"：`effective_feature_num`（有效匹配点数）与 `effective_feature_ratio`（有效/候选），以及残差分布 `mean_residual` + `residual_p90`（用 p90 而非均值，因为均值易被大量正常点稀释，p90 对局部匹配恶化更敏感）。判定用**相对滚动基线**：取前 30s 非 drop 帧的中位数做 baseline，判 `rel_num`/`rel_ratio` 相对骤降。不用绝对阈值的原因有两层实证：① 场景间绝对量级差异巨大（corridor 一帧 490 个有效点、single_plane 1068 个、室内更多），绝对阈值不可跨场景泛化；② P5.0 更发现**即便同一场景，first-iteration 与 final-iteration 的分布也完全不同**，P2 冻结的 absolute 阈值在 first-iteration 上会把 normal_indoor 干净帧误拒 99.8%。相对信号（骤降比例）不受场景/迭代点绝对量级影响，才是可迁移的特征。

### 4.5 自适应控制方案类（P3/P4/P5）

**Q14：P3 整体降权为什么必然失败？你从数据里找到的机制是什么？**

A：P3 把测量协方差 R 从常量改成运行时变量 `lidar_meas_cov_ = LASER_POINT_COV × scale`，退化时按 severity 把 scale 放大（几何路 mild 上限 2~10×，匹配路 aggressive 上限 20~100×，取 max 而非相乘避免重复惩罚），等效"少信激光、多信 IMU"。但 median-of-3 A/B 显示：normal 零影响、corridor 无显著差异、single_plane 变差 4.5×、holdout/stress fault 变差 14×/8.7×。机制有三：**①** scalar R 只能改变 LiDAR 与 IMU 的相对信任，**不能创造原本不存在的几何约束**——single_plane 场景"降权"把本来就弱的方向连同强方向一起削弱，等于主动放弃救命信息；**② fault 场景发现了一个正反馈循环**：降权→开始依赖 IMU→IMU 漂移→下一帧 scan-to-map 失配→特征数骤降被误判为"匹配失败"→继续降权→发散（标定期误差从 1m 涨到 10m，exp_059 里 clean 段居然触发 match_scale 15.9×）。我加的"连续降权 3s 上限"能打破循环（10m→1.4m），但改变不了本质；**③ 雷达坏 ≠ 该靠 IMU**：长 10s 的故障里纯 IMU 能漂好几米，而"将就着用坏雷达剩余 10%~20% 的有效点"误差反而只有 0.1~1m。最终结论：整体降权的能力边界 = 只对轻微 RPE/final drift（cm 级）有效，严重场景确定性有害。

**Q15：P4 方向性抑制和 P3 的区别？为什么改在 ESKF state correction 层而不是改 Jacobian？**

A：P3 是"整帧降权"（scalar R 放大），P4 是"只压弱方向"：把 ESKF 解出的状态修正 dx 沿 weak direction 投影 `Π_β(v)=v−(1−β)(v·w_t)w_t`（β 是弱方向保留系数，β=1 就是原版），强方向完全保留，同时把 Kalman 增益 K_x 的 pos 行做同样的列投影，使协方差更新 `P=(I−K_pH)P` 不自相矛盾。为什么改 state correction 而不是把测量 Jacobian 的弱方向分量改小：我一开始确实想改 Jacobian，但先写了一个 1D/2D 数值 sanity test（`p4_sanity_1d2d.py`），**证明 Jacobian scaling ≠ correction suppression**——把 h_x 的某方向分量缩小，解出来的修正量在那个方向反而可能被放大（最多 2~10×），因为卡尔曼增益里 P 与 H 的耦合非线性。这是典型的"改对地方"的教训：在解出修正量之后、boxplus 之前投影，语义才直观可控。同时加了 matching gate：只有 `geometry_bad ∧ matching_ok`（P2 判不是匹配失败）才允许抑制——因为匹配失败时算出来的 weak_direction 本身可能失真。gate 的有效性被 fault 实验确认：fault 段 71% 帧被正确阻断，clean 段 68% 正常触发。

**Q16：P4 结果如何？方向性抑制也失败说明了什么？**

A：结果：normal/corridor 安全（持平）；single_plane holdout（新录 bag）**变差 3.7×**（2.58m→9.53m）；fault 场景有 15~50% 改善倾向但样本方差大、机制不明，不能作为有效证据。关键的是失败机制分析：single_plane 里 weak_direction 每一帧都稳定指向同一方向（相邻帧 |dot|=1.0），说明**不是方向估计错了**；但"弱约束 ≠ 有害约束"——scan-to-map 沿弱方向的残差即使噪声大，也一直在约束状态的相对一致性、防止 IMU 在该方向死区漂移；完全抑制它等于在不可观测方向只信 IMU，而 IMU 在那个方向本来就不可观测（single_plane 中 y 无任何信息源）。还有一个二阶效应：即使 K 行投影保持了协方差一致性，P 沿弱方向保守反而让下一帧 IMU 先验权重上升，状态更快漂向 IMU——**保守的协方差在退化方向加速了"放弃激光"**。与 P3 合起来得到强结论：任何"把状态估计从 LiDAR 弱约束交给 IMU"的操作（整体降/方向降/拒绝）在 IMU 精度有限时都是净损失。

**Q17：P5 的 current-frame 拒绝机制怎么实现？为什么持续 fault 下反而更差？**

A：实现上，在 `esekfom.hpp` 的 `update_iterated_dyn_share_modified()` 加一个 `first_iter_gate_cb` 回调：第一次迭代（i==-1）的 `h_dyn_share()` 完成、得到 KD-tree correspondence 与 first-iteration 统计后、计算 K 之前调用。判定为坏测量时执行**显式恢复**：`x_ = x_propagated; P_ = P_propagated; *measurement_rejected = true; return;`——状态与协方差等价于"本帧从未见过 LiDAR"，只剩 IMU propagation，且跳过该帧 ikd-Tree 地图插入（防污染）。判定通道是 first-iteration 的相对信号：`(rel_num<0.40 OR rel_ratio<0.30) AND (rel_p90>2.0 OR mean_residual>0.02)`，**AND 语义**是调出来的关键——单看"点少"会把 dropout 帧误拒（V5 曾因此 165m 发散），只有"点少且残差差"才是真匹配失败。另配了恢复状态机：NORMAL→REJECT_ONCE→DEGRADED(连续≥2)→RECOVERY_REQUIRED(连续≥5)，RECOVERY_REQUIRED 后允许重新插图避免"地图冻结→永久失配"。A/B 结果：normal/single_plane **0 拒帧、轨迹数值等价**（gate 关闭路径无损）；但 V5 持续 fault 下 0.086m→2.28m（26×）、stress 1.84m→10.7m（5.8×）。原因：原版 FAST-LIO 对这种强度的 fault（outlier 8%/dropout 80%/noise 0.15）本就足够鲁棒（ATE 8.6cm），拒绝反而触发"拒绝→纯 IMU 漂移→匹配更差→继续拒绝"的负反馈；噪声段坏点会被平面拟合剔除，残差正常导致 gate 判定困难。这是机制性问题，试了多种阈值组合都救不回来——与 P3/P4 共同构成完整的科学结论。

**Q18：如果把 P1~P5 浓缩成"你对 LIO 退化的研究结论"，你怎么说？**

A：三层递进。**第一层（检测）**：几何可观测性弱可以靠滤波器内部的 geometric Hessian 特征结构精确量化（trans_ratio/weak_direction），外部几何代理做交叉验证；**第二层（归因）**：必须把"环境几何退化/传感器匹配失败/IMU 激励不足"三类风险源分开，用多标签+severity 表达复合故障，并且"检测到退化"与"误差变大"要解耦、用 GT 量化后果；**第三层（控制/自适应）**：我们用严格 A/B 证明了一个反直觉结论——对 FAST-LIO 这类已经很强壮的滤波器，介入式防护（降权/方向抑制/帧级拒绝）在信息缺失与持续故障场景都难以超越原版，真正有价值且被验证有效的是**检测与门控**（把风险源识别出来、阻止错误机制乱动），而不是在状态估计层面干预。这也解释了为什么工业界更愿意在 LIO 外面做"健康监测+重定位兜底"，而不是改滤波核。

### 4.6 全局重定位与导航类（主线一）

**Q19：为什么选了 KISS-Matcher + small_gicp 的组合？初始化与跟踪是怎么切换的？**

A：需求是"任意位置开机、无人工初值即可重定位"，这正是全局配准问题。KISS-Matcher（MIT-SPARK，ICRA 2025）是做**无初值粗配准**的：对地图与当前扫描分别构建基于关键点/法向一致性的描述子并用高效搜索找候选对应，再做 coarse-to-fine 配准，输出一个可作为初值的位姿——它强在"无初值、全局"，但作为里程计级连续跟踪太重且不够平滑。small_gicp 是轻量并行 GICP 实现，适合以初值做**连续跟踪**。所以架构是两阶段状态机：**初始化**——累计 `/registered_scan`（机器人原地转/短移增加重叠），按 `voxel_resolution` 降采样后调 KISS-Matcher `coarseToFineAlignment()`，成功后记日志 `KISSMatcher initialization succeeded` 并验证（`verify_kiss_with_gicp`）；**连续跟踪**——用 small_gicp 以上一帧位姿为初值做 VGICP，发布 `map→odom`；当 GICP **连续失败超过 `gicp_max_consecutive_failures=2`** 时自动切回 KISS-Matcher 做全局恢复（带 `recovery_cooldown_sec` 防止抖振）。另有 RViz `/initialpose` 人工修正通道作为兜底。这样既拿到"无初值开机即定位"，又保证在线平滑。

**Q20：为什么 3D LiDAR 导航要做 3D→2D 切片？代价地图和控制器你怎么配的？**

A：Nav2 本体是 2D 导航栈（costmap 是 2D 栅格、planner 在 2D 规划），而我们传感器是 3D 点云。做法是在 `Pointcloud2d_3d.yaml` 里配置切片高度带与角分辨率，用 `pointcloud_to_laserscan` 把 `/registered_scan` 落到机器人所在高度附近的一个 2D 平面（`/scan`），既保留 3D LiDAR 的大视场（比真实 2D 雷达信息多），又无缝喂给 Nav2。代价地图配了全局与局部两张：全局为 0.05m 栅格（静态层加载 pgm 地图 + 障碍物层实时 `/scan` + 膨胀层 0.55m），局部为 6×6m@0.05m 滚动窗口（`global_frame: odom`，20Hz 更新）。规划用 NavFn（全局，Dijkstra）、DWB（局部，20Hz 发 `/cmd_vel`，用轨迹采样的方式做速度空间评分），BT 用 `navigate_to_pose_w_replanning_and_recovery.xml`，带 spin/backup 等恢复行为。另外因为有独立里程计（LIO）+ 重定位（map→odom），**导航栈不需要 AMCL**，map→odom 由我们自己的重定位节点发布——这也是"3D LiDAR 导航"相对"2D 雷达+AMCL"方案的差异点。

**Q21：仿真与实机如何做到"仅换驱动"？你遇到过哪些仿真-实机差异？**

A：两层抽象：① 传感器驱动抽象——仿真用 Gazebo 的 ray 传感器插件（`livox_laser_simulation_RO2`）发布与实机同名的 `/livox/lidar` 话题；实机用 `livox_ros_driver2`（读 `MID360_config.json` 的 IP）。② 机器人描述抽象——仿真用 `get_urdf` 的 `simple_car.urdf`，实机用 `gld_robot_description`（带 RealSense 相机等）。LIO+Nav2+重定位同一套配置，`scripts/mapping_sim.sh` vs `mapping_real.sh`、`nav2_sim.sh` vs `nav2_real.sh` 各自一键。需要注意的差异：仿真必须 `use_sim_time=true`（读 `/clock`）而实机 false；FAST-LIO 用 `xfer_format=0`（PointCloud2）而 Point-LIO 需要 `xfer_format=1`（Livox CustomMsg），两者 `lidar_type` 枚举定义不同不能混用；Point-LIO 仿真还需要 `ign_sim_pointcloud_tool` 注入 ring/time 字段。实机侧驱动链路（livox_ros_driver2 + `gld_robot_description` 实机 URDF）已就绪并单独联调过（期间修复过 Livox-SDK2 编译问题），退化研究部分刻意放在仿真，是因为需要可控几何 + 精确真值。

### 4.7 ROS2 / C++ 工程类

**Q22：你改了 FAST-LIO 的核心头文件，怎么控制改动风险的？**

A：三层防线。**第一层：零侵入默认值**——所有新逻辑 `enable=false` 时在数值上与上游等价，且只通过 launch 参数（`mapping.launch.py` 的 `adaptive_*`/`directional_*`/`robust_gate.*`）打开，不新增 yaml 配置源（吸取 P2 里 yaml 嵌套块被 launch 覆盖导致"文档配置不生效"的教训，做到**参数单一事实源**）；**第二层：数值验证**——每个机制配 synthetic test（把逻辑从滤波器中抽出来单测，P4 十条断言、P5 六个场景全过）和 **C++/Python parity check**（同一 bag 帧级对比 C++ 实际输出 vs Python 独立实现，P3 max|err|=5e-6、P4 535/535 帧 100%）；**第三层：A/B 纪律**——正式对比只信 median-of-3，只承认超过运行噪声的差异。改第三方源码最重要的原则：**先证明"我改对了/改坏了都没影响原行为"，再谈"改进有效"**。

**Q23：自定义消息接口包怎么组织？为什么把接口单独放一个包？**

A：`src/lio_interfaces/` 是纯接口包（ament_cmake + rosidl），成员 `rosidl_interface_packages`，4 个 msg 按用途分：`DegeneracyScore`（P1 分数）、`DegeneracyIteration`（IEKF 迭代过程 debug 观测）、`LioHealth`（P2 健康信号聚合，含 P3/P4/P5 扩展字段）、`ErrorAttribution`（P2 归因输出）。单独成包的收益：`fast_lio`（生产者）与 `lio_evaluation`（消费者）共同依赖它，**依赖方向不会倒置**——核心算法包不依赖评测工具包，评测工具包依赖接口包即可；字段注释里写清理论口径与坐标系约定，接口即文档。为兼容 git tag（p2-final 等）冻结后新增字段，LioHealth 采用"向后追加字段"策略，recorder 与旧分析脚本保持兼容。

**Q24：评测链路里 C++ 和 Python 怎么分工？性能够吗？**

A：**C++ 做实时关键路径**：fast_lio 内嵌逻辑（Hessian/health/gate）与 `degeneracy_proxy.cpp`（外部代理检测器，kNN/PCA 每帧算）都必须低延迟；**Python 做编排与离线分析**：run_experiment（进程编排/launch/参数快照）、recorder/monitor（数据落盘，10Hz 量级）、compute_metrics（离线 evo 评测）、批量 A/B、绘图聚合。实时性验证过：退化检测只读 h_x 做特征分解（6×6 矩阵），自适应控制只是少量算术，monitor 记录的 CPU/帧耗时与 baseline 无显著差异（fast_lio 主循环 ~10Hz/100ms，退化场景极端帧出现 900ms 尖峰是特征剔除/迭代收敛变慢，属场景特性而非我们的代码开销）。

**Q25：说说你怎么排查"机器人实验跑不满 90s / 数据报废"这一类工程问题？**

A：这类问题分三层定位。**运动层**：脚本盲目驾驶会撞墙/卡死/翻车，我写了 `drive_node`（订阅 `/livox/lidar` 前向 ±60° 锥 + 高度带 [-0.15,0.5]m 检测，stop_dist 0.8m 触发、每次只转 30° 步进避障、clear_dist 1.2m 恢复；wander 前进 3.2m 转 30° 增加覆盖；1s 无雷达自动停车防盲跑；20Hz 加减速斜坡平滑输出）。**健康层**：`health_watch` 看门狗记录/中止翻车（|roll|或|pitch|>0.9 rad）、卡死（有指令但 15s 位移<0.1m）、RTF 低（<0.9）。**仿真层**：把 Gazebo 物理步长 0.001→0.002、`real_time_update_rate` 1000→500、关阴影、调大轮子加速度、垂直激光采样 50→24（仍处真实 MID-360 点数级，ATE 不变验证无损）。效果：normal_indoor 90s 有效数据从时长短/撞墙变成稳定 94s、轨迹 22.4m、覆盖面积扩大约 4 倍、零翻车。这条经验说明：**算法实验的上限取决于数据采集基建的可靠性**。

## 5. 个人突出贡献与踩坑复盘

### 5.1 最突出工作一：从 0 到 1 自研"退化感知 LIO 全链路"并建立可复现的算法评测体系（P1→P5，最有含金量）

**做了什么事（一句话）**：在不动 FAST-LIO2 核心数值路径的前提下，围绕"几何退化"这一个 SLAM 经典难题，打通了**检测（P1）→ 归因（P2）→ 自适应控制（P3/P4/P5）→ 真值评测**的完整研究闭环，最终用 175 个受控实验把三条主流"自适应"路线系统证伪，收敛出"检测+归因+门控才是有效路径"的结论。

**为什么突出**：
- **学术纵深**：不是调参试用，而是深入到 ESKF/IEKF 内核，用真实参与更新的测量 Jacobian 构造 geometric Hessian（Ht/Hr/H6），从信息论/可观测性角度量化退化方向；并正确处理了弱方向坐标系（平动=世界系、转动=body 系）、特征向量符号歧义（Ht 时间累积）、协方差一致性（K 行投影）等容易被忽视的细节。
- **方法学严谨**：fault injection + 标定集/验证集分离 + median-of-3 + precision/recall + C++/Python parity + synthetic test，六件套全部到位；"退化≠必然大误差""整体降权在严重场景确定性有害"等结论均有数据支撑且可复现（每个实验目录自含参数快照）。
- **诚实交付**：P3/P4/P5 三个阶段的结论如实呈现（含负面结果），并给出机制层面的解释（正反馈循环、"弱约束≠有害约束"、拒绝→漂移负反馈），而非为了"好看"隐藏。

**可量化成果（面试背这些数字）**：
- 健康室内环境退化检测 0 误报（normal_indoor/bookstore/hospital 双检测器 degraded_ratio=0.0%），正常定位精度 ATE 0.010~0.153m；
- 三类受控退化场景全部被正确报出且与误差趋势一致：corridor（ATE ~0.10m）/ single_plane（1.75m）/ open_ground（1.79m）；
- 误差归因：干净走廊 recall 1.00、normal 室内无 flag 误报、fault 注入 precision 全部 1.00、held-out fault recall 0.77；
- 自适应 A/B（median-of-3）：P3 normal 零影响/single_plane 变差 4.5×/fault 变差 8.7~14×；P4 single_plane holdout 变差 3.7×、fault 改善 15~50%；P5 clean 与 geometry 场景 0 拒帧零侵入、持续 fault 劣于 degen（5.8~26×）——三条路线边界全部量化。

### 5.2 最突出工作二：端到端 3D LiDAR 自主导航系统 + 多场景仿真/真值实验底座

**做了什么事**：从环境搭建开始，把"四轮滑移机器人 + Livox MID-360"做成一套**仿真与实机一致性**的完整系统：双 LIO 里程计可切换、SLAM Toolbox 在线建图与 PCD 3D 地图、KISS-Matcher+small_gicp 无初值全局重定位（任意位置开机）、Nav2 导航（NavFn+DWB+三层 costmap）、GUI 遥控与全套一键脚本。在其上还构建了多室内场景仿真平台（4 张 RoboMaker 高保真地图 + 182 个模型自包含 + P3D 真值桥接），为后续算法研究提供了"健康基线+受控退化+真值"三合一的实验底座。

**为什么突出**：
- **广度与完整度**：一条数据链覆盖传感器驱动→里程计→坐标桥接→建图→重定位→规划控制，能回答"从雷达原始点到机器人运动"的每一个环节问题；TF 树、消息流、文件组织都清晰可讲。
- **解决真实工程难点**：全局重定位从"必须给初始位姿"做到"任意位置开机自动定位"（5/16~5/22 攻坚，含初始化→连续跟踪→失败自动回退的状态机）；仿真模型从"依赖外部绝对路径、启动即崩"做到"包内自包含、四个地图参数一键切换"（修了 Spotlight mesh 大小写 bug、bookstore 内置机器人冲突、gzclient 缺 media 路径崩溃等一串问题）。
- **直接复用**：研究主线（P1~P5）的所有实验都是在这套底座上跑的；没有这套 GT 基建，后面所有"厘米级结论"都不成立。

### 5.3 项目中出现的问题与我的解决方式（准备 4 个，均可展开讲 2~3 分钟）

**问题 1（最有价值）：P3 标定期发现"降权会自己害自己"的正反馈循环（降权→IMU 漂移→失配→误判匹配失败→继续降权→发散）**
- 现象：雷达故障段一降权，误差从 1m 涨到 10m；进一步分析发现连 clean 段都出现 match_scale=15.9× 的误触发。
- 排查：把 exp_059 的时间轴逐帧对齐 scale / residual / 特征数，定位到"降权→漂移→特征数骤降→误判→继续降权"的闭环；确认这不是阈值标定问题而是机制问题。
- 解决与沉淀：给连续降权加 3s 时长上限，到点强制恢复激光主导，发散被按住（10m→1.4m）；但更重要的是把结论升级——**该机制问题意味着"整体降权"路线本身有缺陷**，直接为 P4 方向性抑制立项提供了数据依据；随后 P4 又在 state 层证明了"方向性抑制也无法缓解信息缺失"，最终把研究方向收敛到"检测/归因"。
- 体现能力：能从实验异常中区分"实现 bug / 参数问题 / 机制缺陷"三个层次，并把偶发发散提炼成可复用的设计约束。

**问题 2：评测基建类 bug 叠加（drive 模式失效 + 时间基准错位 + bag 混入旧信号 + 回放非确定性）**
- 现象一：`run_experiment` 的 `--drive` 参数映射错误，导致 exp_032/033 名义上是"匀速/走停"实验、实际在漫游——靠核对驱动日志与 IMU 数据模式才发现。
- 现象二：fault injector 的 t0 与 health 时间戳起点不一致，故障效应错位 1~3s，召回率被低估一半——修复：统一减首帧时间 + 故障段 ±3s 缓冲。
- 现象三：canonical bag 误录了 `/lio/health`，回放时旧信号与新信号双路混合，把故障效果稀释（fault 检出 0.00）——修复：bag 只保留原始 lidar/imu/gt 三话题，重录后检出恢复 0.65。
- 现象四：FAST-LIO 同一 bag 回放 3 次 ATE 0.104~0.204m 浮动——一开始误以为"两次回放完全一致"，第三次运行露馅。
- 解决：逐一修复后，把"同一输入多次回放取中位数、只承认超噪声差异"写死为全项目 A/B 纪律，并把每份参数/commit 快照锁进实验目录。
- 体现能力：对"实验结论可信度"有洁癖——这些 bug 全部是验证流程自己逼出来的，说明这套验证流程有效。

**问题 3：Gazebo 仿真数据采不上来（小车撞墙翻车、画面卡顿、有效时长不足）**
- 现象：脚本盲目驾驶，机器人撞墙/卡死/翻车，FAST-LIO 数据报废；RTF<1 且 GUI 卡顿。
- 解决：运动层写 `drive_node` 反应式避障漫游（前向锥点云检测 + 30° 步进转向 + 迟滞恢复 + 无雷达停车）；健康层写 `health_watch` 看门狗（翻车/卡死/RTF 事件记录 + 可选中止）；仿真层做物理步长/更新率/阴影/激光分辨率一揽子调优。效果：normal_indoor 有效实验稳定 94s、轨迹 22.4m（+27%）、探索面积扩大约 4 倍、零翻车；还修了 GUI 遥控的 `rounded_rect` 渲染 bug。
- 体现能力：算法岗同样需要把"数据采集"当工程做——90s 干净数据的稳定性是后面一切实验的前提。

**问题 4：仿真模型与地图的资源地狱（绝对路径依赖、大小写、模型缺失、gzclient 崩溃）**
- 现象：新增的 RoboMaker 室内地图要么 `model://` 解析失败，要么 mesh 加载失败、要么 gzclient 因缺 Gazebo media 路径直接崩溃。
- 解决：把 182 个模型合并去重后**移入工作区包内**（`src/get_urdf/models/`），`gazebo_resource_root` 默认值改用 `FindPackageShare()` 自动解析，GAZEBO_MODEL_PATH / GAZEBO_RESOURCE_PATH 在 launch 内自动拼接，去掉一切外部绝对路径；修复了 upstream 的 `Spotlight_01` 文件名大小写 bug（Linux 大小写敏感）；注释掉 bookstore 内置的第二台机器人；对 4 个 world × 182 个 model.sdf 做静态引用扫描（`Unable to find` 计数 = 0）与 headless gzserver 冒烟验证。
- 体现能力：环境可移植性/可复现性思维——让"换台机器也能一键起"成为默认标准。

**备用问题 5：评测工具本身有 bug（姿态误差虚高）**
- 现象：`directional_analysis.py` 里 rot_err 在带 yaw 出生的场景虚高到 90°（indoor_room 出生 yaw=1.57）。
- 原因：姿态误差用了**未对齐**的原始四元数，而位置误差用了 Umeyama 对齐后轨迹；GT 从出生 yaw 开始、LIO 从 yaw=0 开始。
- 解决：改用对齐后姿态（`est_sync.orientations_quat_wxyz`）计算旋转误差，修复后 indoor_room rot_err 从 90.08° 降到 0.71°；同时诚实记录遗留限制（直线往返轨迹下 Umeyama 旋转分量欠定，转弯丰富的轨迹才可信）。

### 6.3 风险问题诚实应对（面试官可能的"进攻"方向）

1. **"你这个仿真占比很大，实机做过什么？"** → 实机部署链路完整存在（livox_ros_driver2 + gld_robot_description + nav2_real/mapping_real 脚本），实机驱动层联调过（期间修复过 Livox-SDK2 编译问题）；选择仿真做退化研究是因为**需要可控几何 + 精确真值**，这两点在实机上都无法获得（实机只能给稀疏的位姿真值）。如果公司有实机条件，退化检测/归因模块是零侵入的，可以直接移植部署。
2. **"退化检测/归因是 rule-based 阈值，为什么不学个分类器？"** → 三个原因：① 可解释性——SLAM 故障链路复杂，规则每条都可溯源到物理信号（特征值/残差/IMU 激励），P3 之后发现"归因必须能解释"是硬需求；② 数据——故障样本在实机是长尾稀缺事件，rule-based 不依赖大规模标注；③ 工程可移植——零侵入 + 无 ML 依赖，任何 LIO 工程可直接抄走。同时我把所有阈值都做成配置 + 标定/验证分离流程，如果未来有数据，规则输出的 margin 完全可以作为特征喂给 ML 做融合。
3. **"你证伪了三条路线，那你的改进到底有没有提升 ATE？"** → 坦诚：P3/P4/P5 在"降低 ATE"这个目标上没有赢（这正是我们要的结论）；**被验证有效的正向产出是检测+归因+门控**（P1 三类退化 0 漏检可解释、P2 precision 1.00、P4 gate 阻断 71% 故障帧），它们的价值是**风险预警与系统级鲁棒性**（触发重定位/降速/告警），不是滤波器内部精度。这个诚实边界反而比"宣称提升 30%"更可信。
4. **"这些代码有多少是你写的 vs 抄的开源？"** → 导航/仿真主线基于开源（FAST-LIO2、Nav2、KISS-Matcher、slam_toolbox）集成与二次开发；**研究主线的检测器、归因规则、三层框架、评测闭环、全部实验分析代码是自己从零写的**（`lio_interfaces` + `lio_evaluation` 两个包 + FAST-LIO 三处内核改造）。集成类工作量的价值在于系统打通与排错，研究类工作量的价值在于算法与实验设计。

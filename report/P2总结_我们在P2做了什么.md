# P2 总结：我们在 P2 做了什么

> 面向对象：刚接手项目、没看过 P2 代码的人。看完这篇，你不需要懂 LIO 细节，
> 也能说清楚 P2 到底解决了什么问题、怎么验证的、哪些结论可信、哪些坑我们踩过。

---

## 一、先讲背景：P1 给定位算法装了个"报警器"，但它只会说一句话

回忆 P1：FAST-LIO 是激光雷达 + IMU 的定位算法，相当于一个蒙着眼、靠激光尺子摸墙走路的机器人。

P1 干的事，是给这个机器人装了一个**"几何信息报警器"**。它守在旁边，盯着算法内部那个叫
"约束矩阵 H"的东西，判断：

> 现在这个地方的墙，够不够告诉我"我在哪"？
> 如果不够（比如在**长走廊**里，前后方向的信息约等于没有），报警器就喊：
> **"退化啦！"**

但是——P1 的报警器**只会喊这一句**。它不知道：

- 这次退化，到底是**墙没信息**（几何问题）？
- 还是**雷达信号坏了**（匹配问题）？
- 还是**机器人压根没在动**（IMU 问题）？

更不知道退化**有多严重**、误差会不会真的变大。

这就是 P2 要解决的问题：**从"报警"到"归因"——把报警的原因说清楚、把后果量出来。**

---

## 二、P2 到底在做什么？一句话版

> **P2 = 让报警器学会"分诊"：既能报"哪里不舒服"，又能报"为什么不舒服"、
> "有多严重"，并且全程不碰定位算法本身（只看、不改）。**

P2 搭了一条完整的流水线，叫"三层框架"：

```
① 健康信号 (Health Signal)    →  FAST-LIO 每帧自报的各项体检指标
        ↓
② 误差归因 (Error Attribution) →  把指标翻译成"原因 + 严重程度"（本阶段核心）
        ↓
③ 误差后果 (Error Consequence) →  离线算：这个原因下，误差到底有多大
```

打个比方：**① 是体温计读数，② 是医生诊断"你感冒了，中重度"，③ 是住院观察"感冒确实让你难受了 3 天"。**
P2 主要做的是 ②，并把 ①②③ 串起来验证。

---

## 三、报警器现在能认出哪几种"病因"？

P2 给报警器培训了**三种病因**（专业名叫 flags，它们可以**同时成立**，这很重要）：

| 病因 | 通俗解释 | 它看什么指标 |
|---|---|---|
| **GEOMETRY_DEGENERATION**（几何退化） | 墙太平、太长、太对称，定位"抓瞎" | 约束矩阵强弱方向比（P1 那套） |
| **CORRESPONDENCE_FAILURE**（匹配失败） | 雷达坏了/信号脏，扫出来的点对不上地图 | 有效特征数骤降、残差飙升 |
| **IMU_LOW_EXCITATION**（激励不足） | 机器人静止/匀速，IMU 提供不了运动信息 | 陀螺仪/加速度计的激励大小 |

**"可以同时成立"不是 bug，是真实世界的样子。** 你在走廊里停着不动，
这时候"几何退化"和"IMU 激励不足"**同时存在**。硬要二选一反而是错的。

所以 P2 的最终输出是：

- **多标签 flags**：`is_geometry_degen`、`is_matching_failure`、`is_imu_low_excitation`
  各自独立地"是/否"——**这是 P3 真正要用的核心结果**；
- **severity 分数**（0~1）：每个病因的严重程度（越大越严重）；
- **dominant_risk_label**（主导风险标签）：severity 最高的那一个，**只是个"摘要"**，
  用来给人看、给图着色，不是互斥的"金标准分类"。

> 为什么这样设计？因为后面 P3 要让定位算法**根据病因调整自己**（比如匹配坏了就少信雷达、
> 几何退化就只压弱方向的修正）。如果只给一个"主标签"，就会丢掉"几何退化和 IMU 低激励
> 同时存在"这种复合信息。多标签 + severity 才能支撑自适应。

## 四、怎么证明它"判得准"？—— 两层验证 + 人为搞破坏 + 用没见过的数据考它

光说"能认病因"不够，得拿出证据。P2 用了三招：

### 招数 1：人为搞破坏（fault injection）

把激光雷达**人为弄坏**，而且坏法要"有剧本"：

```text
第 20~30 秒：扔掉 90% 的激光点（dropout）—— 像下大雾
第 40~50 秒：只留正前方窄缝（fov_crop）—— 像望远镜镜筒挡住
第 60~65 秒：往点云里掺 12% 的离群点（outlier）—— 像脏点乱飞
第 75~85 秒：给所有点加噪声（noise）—— 像信号雪花
```

**关键点**：这些破坏是**已知的、定时的、可复现的**（用固定随机种子）。
所以我们知道"标准答案"：`dropout 时段 → 应该是匹配失败`。
然后看报警器能不能在那些时段喊出"匹配失败"——这就是"第一层验证：分类对不对"。

### 招数 2：用没见过的数据考它（hold-out）

作弊是不允许的。所以：
- **调参数**只允许用一套"标定集"数据（`corridor_run1`，代号 C）；
- 调完参数后，用**从没参与调参的"验证集"**（新的走廊、室内地图、单面墙）来考它，
  代号 V1~V5。

如果参数在标定集上调"过拟合"了，验证集一考就露馅。这就是为什么实验有几十个编号——
它们各自有分工：标定、验证、复现。

### 招数 3：两层验证

- **第一层（分类正确性）**：报警器喊的原因，和"标准答案"对不对得上？
  统计两个数：`precision`（喊对了没——喊了 100 次，几次是真的）和 `recall`（漏没漏——该喊的 100 次，喊了几次）。
- **第二层（后果严重度）**：这个原因下，定位误差到底有多大（厘米级？还是漂出好几米？）。

## 五、成绩单（冻结阈值后的最终数字）

**最硬的一条：所有场景的 precision 全是 1.00——报警器一次都没有误报。**

| 场景 | 该喊什么 | 检出了吗（recall） |
|---|---|---|
| 干净走廊 | 几何退化 | **1.00**（全检出） |
| 正常室内 | 什么都不该喊 | **正常标签 0.93**（没有 flag 误报） |
| 单面墙（严重退化） | 几何退化 | **1.00** |
| 强化人为故障（C3） | 匹配失败 | **0.72**（误差 4.08 m，故障真的大） |
| 陌生故障（V5，held-out） | 匹配失败 | **0.77** |
| 回放陌生故障（replay） | 匹配失败 | **0.65** |

其中"匹配失败"没到 100% 的原因很诚实：故障的**实际效果**和"剧本时间"有 1~3 秒的
错位（注入链路的时间基准问题），属于实验误差，不是报警器漏。质量型故障（脏点/噪声）
的检出率是 **1.00**。

还有一个重要的"非结论"——**"退化 ≠ 必然出大错"**：

- 走廊退化 → 误差只有 3~4 厘米（退化了，但算法还能扛）；
- 单面墙退化 → 误差 7 米（同样退化，这次真的废了）；
- 人为故障 → 误差 4 米（雷达坏了就是坏了）。

所以报警器只是**报告风险**，后果由真值数据如实量化。这一点 P2 反复强调，
因为它是后面 P3"自适应"的立足点：**不是所有退化都要猛改，要看后果严重度来定权重。**

## 六、报警器的"灵敏度"是怎么定的？（阈值标定）

报警器判断"这个指标算不算异常"要用到一堆阈值。P2 的原则是**分路标定，各管各的**：

| 病因 | 用什么数据调阈值 | 原则 |
|---|---|---|
| 几何退化 | **不动**（P1 已经标好） | 不为 P2 好看而改 P1 的结论 |
| 匹配失败 | 只用故障标定集 C3 | 目标：故障段 recall 高；**验证集 V5 绝不参与调参**（防数据泄漏） |
| IMU 激励 | 按**运动状态**（真静止/真匀速/真转弯） | 用"机器人实际在不在动"来调，**绝不用定位误差反过来凑阈值** |

特别是 IMU 那一路，我们故意**不用误差去调**，因为那样会让"激励不足"变成"误差大"的
同义反复。我们用 stop_go（走 8 秒停 4 秒）和匀速直行两个实验，标定结果是：
**真静止时 100% 命中、转弯时 0% 误报**——报警器确实在说"机器人没在动"，不是在说"误差大"。

## 七、"神秘实验文件夹"里多了什么？

P1 每个实验文件夹已经有一整套档案。P2 又加了：

```text
experiment_XXX/
├── lio_health.csv           ← 新增①：FAST-LIO 每帧的"体检报告"（健康信号）
├── error_attribution.csv    ← 新增②：归因结果（flags + severity + 主导标签）
├── attribution_report.yaml  ← 新增③：两层验证的成绩单（precision/recall/误差分布）
├── attribution_distribution.png ← 新增④：时间轴图（标签 + 误差曲线）
├── scenario_annotations.yaml   ← 新增⑤："标准答案"（哪个时段该是什么原因）
├── attribution_params.yaml     ← 新增⑥：这次实验用的归因阈值快照
└── config.yaml                 ← 新增⑦：resolved 参数快照（health/阈值/故障配置）
```

**为什么这么厚？** 因为做科学实验必须能回答"这张图是哪一版代码、哪一套参数跑出来的"。
P2 收尾时我们特意加了"参数快照"：每次实验把真正生效的阈值和配置**锁进文件夹**，
而不是靠猜 yaml 和 launch 哪个生效。

另外补了三个 **canonical bag**（`data/bags/` 下的走廊/室内/单面墙三套原始数据包），
这是给 P3 准备的"固定考题"——以后所有算法改动都在同一套输入上考。

## 八、我们踩过的坑（比成功经验更值钱）

1. **驱动模式 bug**：实验脚本里 `--drive` 参数映射错了，导致 exp_032/033 名义上是
   "匀速/走停"实验、实际全在漫游。**发现方式**：查驱动日志 + 看 IMU 数据模式对不上。
   已修复并补做了真实验。
2. **时间基准错位**：故障注入器的"第 20 秒"和健康数据的时间戳不是同一个起点，
   导致召回率被低估了一半。**修复**：统一减去首帧时间 + 故障段取 ±3 秒缓冲。
3. **数据包混入旧信号**：canonical bag 里误录了 `/lio/health`，回放时旧信号和新信号
   混在一起，把故障效果"稀释"了。**修复**：bag 只保留原始 lidar/imu/真值。
4. **FAST-LIO 运行有非确定性**：同一个 bag 回放三次，ATE 在 0.10~0.20 米之间浮动，
   帧数也不完全相同。**含义**：以后 P3 做 A/B 对比，不能跑一次就下结论，
   必须**同一输入跑多次取中位数**，并且只承认超过这个"运行噪声"的改进。
   （我们一开始误以为两次回放"完全一致"，第三次运行就露馅了——结论已撤回并写进报告。）

这些坑恰恰说明：**P2 的验证流程是有效的——它能逼出这些隐蔽问题。**

---

## 九、一句话总结 P2

> **P2 干的事 = 给 P1 的"退化报警器"装上"分诊"能力：能同时报出几何退化、
> 匹配失败、IMU 激励不足三种病因以及各自的严重程度，用人为故障 + 陌生场景两层
> 验证证明它"不误报、漏检可控"，把阈值、参数、数据包、代码全部冻结成可复现的
> 实验底座，交给 P3 去真正"动手"（自适应权重）。**

P3 要做的事也提前剧透：拿到 P2 的 flags + severity 之后，让 FAST-LIO 在
"匹配坏了"时降低激光权重、在"几何退化"时只压制弱方向的修正，然后在
canonical bag 上用"多次运行取中位数"的规矩做严格 A/B。
